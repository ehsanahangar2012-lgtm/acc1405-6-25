# راهنمای امن‌سازی نسخه‌های انتشار

## محافظت کد

- ساخت‌های Windows و Android پیش از بسته‌بندی، JavaScript خروجی را مبهم‌سازی می‌کنند.
- خروجی Vite بدون source map ساخته می‌شود و اسکریپت انتشار وجود فایل‌های `.map` را بررسی می‌کند.
- Windows با ASAR بسته‌بندی می‌شود و DevTools در نسخهٔ بسته‌بندی‌شده غیرفعال است.
- Android در حالت Release از R8/ProGuard و کوچک‌سازی منابع استفاده می‌کند.

مبهم‌سازی، استخراج و تحلیل کد را دشوارتر می‌کند اما آن را ناممکن نمی‌سازد؛ رشته‌ها، رفتار برنامه و کد سمت کاربر همچنان می‌توانند تحلیل شوند.

## امضای Android

برای تولید APK امضاشدهٔ انتشار، این GitHub Actions secrets را تنظیم کنید:

- `ANDROID_KEYSTORE_BASE64`: فایل keystore به صورت Base64
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

بدون این مقادیر، خط لوله فقط APK مبهم‌سازی‌شدهٔ Debug/Test تولید می‌کند و آن را با پسوند `-debug.apk` نام‌گذاری می‌کند. کلید انتشار را در Git یا داخل برنامه قرار ندهید و از آن نسخهٔ پشتیبان امن نگه دارید.

## امضای Windows

برای امضای EXE با گواهی ناشر، این secrets را اضافه کنید:

- `WINDOWS_SIGNING_PFX_BASE64`: گواهی PFX به صورت Base64
- `WINDOWS_SIGNING_PFX_PASSWORD`

بدون گواهی ناشر معتبر، فایل EXE همچنان می‌تواند بسته‌بندی شود اما امضای ناشر نخواهد داشت و ممکن است Windows نمایش هشدار بدهد.

## لایسنس: محدودیت فعلی و معماری موردنیاز

ماژول صدور لایسنس فعلی بخشی از اعتبارسنجی آفلاین را با راز مشترک در کد کلاینت انجام می‌دهد و وضعیت فعال‌سازی هم در ذخیره‌سازی محلی ثبت می‌شود. بنابراین این مسیر قدیمی به‌تنهایی در برابر دستکاری یا جعل مقاوم نیست؛ مبهم‌سازی فایل‌ها این ضعف را برطرف نمی‌کند.

برای لایسنس تجاری مقاوم، مسیر صدور باید به امضای نامتقارن مهاجرت کند: کلید خصوصی فقط در سرور صدور یا ابزار مدیریتی مستقل نگه‌داری شود و برنامهٔ مشتری فقط کلید عمومی را برای اعتبارسنجی امضا داشته باشد. کلید خصوصی نباید در JavaScript، `EXE`، `APK` یا متغیرهای `VITE_*` قرار بگیرد. این مهاجرت نیازمند پیکربندی و آزمون جداگانهٔ صدور/اعتبارسنجی است؛ این تغییرِ ساخت به‌تنهایی ادعای حل کامل آن را ندارد.
