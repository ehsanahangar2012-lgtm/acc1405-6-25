# معماری پیشنهادی نسخهٔ بومی Windows

## لایه‌ها
1. **Presentation — WPF/MVVM:** رابط، binding و ناوبری؛ راست‌چین، Unicode فارسی، اعداد locale-aware و تاریخ جلالی در نمایش. منطق مالی یا شبکه در code-behind/XAML قرار نمی‌گیرد.
2. **Application:** use caseهای ورود، فعال‌سازی، CRUD مالی، گزارش، بک‌آپ و sync؛ مدیریت لغو، خطا و جلوگیری از ثبت تکراری عملیات حساس.
3. **Domain:** قواعد حسابداری، گردکردن پول، مالیات، موجودی و دفترها. انتقال services/accountingEngine.ts تنها با آزمون رفتاری و مقایسه خروجی TS و C#.
4. **Infrastructure:** APIهای HTTPS، persistence محلی، فایل‌ها، بک‌آپ، بازیابی و event logging. استفاده از DPAPI/Windows Credential Manager برای اسرار محلی؛ هیچ راز مدیر مادر یا کلید خصوصی صدور لایسنس در کلاینت ذخیره نمی‌شود.
5. **Contracts:** DTOهای versionable و تطبیق دقیق JSON، null/empty، تاریخ، ارز و quota با سرور.
6. **Tests:** unit tests، golden/contract tests، integration tests برای persistence/license/quota/sync/backup و آزمایش نهایی روی Windows و هاست مجاز.

## تصمیم‌های امنیتی پایه
- HTTPS اجباری؛ اعتبارسنجی گواهی TLS سیستم‌عامل حفظ می‌شود؛ redirect خودکار غیرفعال است.
- token، کلید لایسنس، رمز و محتوای مالی نباید در log قرار گیرد.
- درخواست داده باید در سرور به workspace، دستگاه ثبت‌شده و مجوز فعال متصل باشد. پنهان‌کردن دکمه یا اعتبارسنجی quota در UI کافی نیست.
- مجوز نامعلوم، انقضا، ابطال و quota نباید با fallback آفلاین به دسترسی نامحدود تبدیل شوند.
- مرجع لایسنس به‌صورت ثابت https://acc.ashkghalam.ir است؛ از تنظیمات قابل‌ویرایش مشتری خوانده نمی‌شود.
- از اسرار ثابت در کد توزیع‌شده استفاده نمی‌شود.
- SQLite گزینهٔ بررسی است، نه تصمیم نهایی. انتخاب موتور، تراکنش‌ها، رمزنگاری دیتابیس زنده و سازگاری مهاجرت باید با آزمون مشخص شود. رمزنگاری فایل بک‌آپ به معنای رمزنگاری دیتابیس زنده نیست.

## ترتیب مهاجرت
1. پوسته WPF، ساخت CI و آزمون‌های پایه.
2. DTOها و contract tests؛ سپس کلاینت API و تأیید رسید لایسنس.
3. ذخیره امن credential، ورود و workspace access.
4. مدل‌سازی داده و آزمون مرجع محاسبات مالی.
5. مشتریان، کالا/انبار، فاکتورها و عملیات اصلی با transaction و regression tests.
6. گزارش، import/export، امضا و ماژول‌های وابسته.
7. sync، صف آفلاین و حل تعارض.
8. بک‌آپ و بازیابی با آزمون round-trip و جداسازی workspace.
9. قطع اینترنت، خطای سرور، لایسنس منقضی/لغوشده، ارتقا و حذف برنامه.
10. خروجی مستقل و سپس installer/AuthentiCode در صورت دسترسی به گواهی معتبر.

## معیار پذیرش
- تفاوت توضیح‌نداده‌نشده میان خروجی مالی نسخه مرجع و C# وجود نداشته باشد.
- خطای شبکه، پاسخ نامعتبر، انقضا یا quota به حالت fail-closed و پیام روشن منتهی شود.
- قبل از restore، نسخه/یکپارچگی فایل بررسی و snapshot قابل بازگشت تهیه شود.
- کنترل مجوزهای حساس سمت سرور بماند.
- رابط بومی هیچ WebView/Chromium نداشته باشد.
- وضعیت «رفع و آزموده‌شده» فقط با مدرک آزمون مربوط صادر شود.
